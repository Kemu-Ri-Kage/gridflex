## 3. Cash out before settlement


1. **The two functions.** `mergeSet(amount)` burns a matched YES+NO pair and pays exactly `amount` mUSDT. It is the exact inverse of `mintSet` (BinaryMarket.sol:131-140) and is specified at merge-set-spec.md:45-85. It is allowed in every market state ("Option A", :213-228), needs no approval and doesn't move the pool (:256-285). It adds a new error `InsufficientSet` and a new event `SetMerged`.
2. **Why both are needed.** After a buy a trader holds only one side, so `mergeSet` alone can't exit it (:287-341). The recommended companion is an atomic `sell(bool yes, uint256 amountIn, uint256 minimumCollateralOut, uint64 deadline)`. It swaps inside the market, merges and pays out in one prompt with no approval, and closes when trading closes (:343-384). It still needs its own short spec before it's built (:371-379).
3. **Nothing is built yet.** There is no `mergeSet` or `sell` anywhere in `contracts/src`. The README "What's next" says both ship together in one redeploy (README.md:311-325).
4. **Redeploy implications.** There is no proxy, so existing markets can never gain these functions. It needs a new `BinaryMarket`, a new `MarketFactory` (the factory embeds the market's bytecode), and new markets (merge-set-spec.md:523-542).
   - The current factory `0xE521…C3A9` moves to `legacyDeployments.MarketFactory` in `shared/addresses.json`, where `0xE4d3…0243` already sits.
   - That file then needs the new factory, its `markets[]`, and the top-level `BinaryMarket`/`YesToken`/`NoToken` (:577-584).
   - The old markets stay on chain and must remain resolvable and redeemable.
